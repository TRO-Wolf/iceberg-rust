## Assumptions killed during the audit
1. ASSUMPTION (R-1's recorded reason, taken as universal): 'write_max < max_file_size, so a run-1 output is STRUCTURALLY never re-admitted.' BOUNDED, not killed — it holds wherever the doubles are exact (target, max <= 2^53), which is Java's own convergence argument, but not above: at target = 2^62+513, max = target+1, l2d rounds target up and d2l returns a value above max. Java behaves identically, so C-009 states the scope instead of asserting the universal.
2. ASSUMPTION (R-2 read literally): 'porting inputSplitSize exactly determines the writer feed quantum.' KILLED — inputSplitSize is Java's READ split size; mapping it to the fork's per-write() chunk gives chunks >= target, and because should_roll is a PRE-check output 1 reaches ~134217728 > max_file_size = 120795955 at Java defaults. R-11 then dropped the port entirely and C-025 replaced it with a bounded fork-specific feed; the round-2 S1 is GENUINELY DEAD — at chunk_budget 16384 output 1 lands ~93.95 MB, inside [min, max].
3. ASSUMPTION (prior ledger and panel): 'expectedOutputFiles returns a long.' KILLED — it returns int, narrowing with l2i, and inputSplitSize sign-extends with i2l before ldiv, so a ceiling or floor of exactly 2^32 makes Java throw. PROVENANCE CORRECTED (N-C8): the fork does not port either function (R-11 / C-045), so nothing inherits the divergence and NO C-043 branch pin exists — C-043 is REMOVED.
