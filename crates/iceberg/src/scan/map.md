# map.md — crates/iceberg/src/scan/

## Purpose

Table-scan planning and execution (Java `SnapshotScan` / `DataTableScan` / `BaseFileScanTask`):
snapshot → manifest list → manifest pruning → `FileScanTask` stream → Arrow record batches (the
Arrow read itself lives in `../arrow/`). Includes merge-on-read delete application inputs, residual
propagation, and opt-in scan-metrics reporting.

## Debug

### Known failure modes

| Symptom | Likely cause |
|---|---|
| Task carries the full snapshot filter instead of a reduced one | The residual must be evaluated against the file's partition in `into_file_scan_task` — mutation-pinned; check the per-manifest evaluator wiring |
| Identity-partition constants wrong / type errors in record batches | The `PartitionUtil.constantsMap` constant-materialization path is **active**: each task carries its manifest's `partition_spec` (`context.rs::create_manifest_file_context`), and `arrow/record_batch_transformer` materializes identity-partition columns as PLAIN arrays of the declared scan-schema type (never REE) coerced to the column's Iceberg type (`Datum::to`). A constant field present in the file is forced down the `Modify` path so the constant OVERRIDES the file column (`constant_overrides_file_column`). Wrong value ⇒ check the spec/partition threading and `constants_map`; type/REE error ⇒ check the plain-array + `Datum::to` coercion in the transformer |
| Metrics report emitted on a dropped stream / per task | The report fires ONCE on full consumption (`None` from the stream); early-drop emits NOTHING (pinned by test) |
| No-reporter path changed | With no reporter there must be **no collector, no timer, no wrapper** — the plan path is byte-unchanged (structural test pins this) |
| `plan_tasks` groups diverge from Java | Check the WEIGHT (`task.rs::weight` — delete bytes via `content_size_in_bytes`: DV→blob size, else file size; floor `(1+#deletes)*openFileCost`), the SPLIT branch order (offsets-aware IGNORES target; the passthrough branch is Puffin per Java `isSplittable` PLUS AVRO/ORC per the fork-local `reader_honors_byte_range` — see the duplication row below), the bin-pack eviction (`largestBinFirst`, ties → first-inserted; drain FIFO), AND the adjacent-split MERGE (`task.rs::merge_tasks` in `CombinedScanTask::new` — Java `mergeTasks` in the `BaseCombinedScanTask(List)` ctor). EVERY split sub-task inherits the parent deletes (so deletes are charged per sub-task). If ONE file shows FEWER members on Java than Rust, suspect the merge FIRST: Java coalesces contiguous same-file splits that co-bin (a merged span's start is the run's first start + total length, so it masquerades as an offset SUBSET — decompose the lengths, don't compare starts as a set). Pinned by `bin_pack.rs`/`task.rs`/`task_group.rs` unit tests + the `interop_scan_plan` oracle |
| Wrong rows after partition evolution | The residual (and any per-file logic) must use the FILE's own spec (`partition_spec_by_id(manifest.partition_spec_id)`), never `default_partition_spec()`. A single-spec fixture is structurally BLIND to this swap — use the 2-spec `new_with_evolved_default_spec` fixture to pin it |
| MoR plan hangs forever on delete index | Data tasks park on `DeleteFileIndex` `Notify` (FK2.2 overlap). Lost-wakeup if `Notified` is armed AFTER the read lock (upstream #2696 class); failed-populate hang if state stays `Populating` without `Failed` terminal. Pins: `test_fk2_2_*` + SAF-007 suite in `delete_file_index.rs` |
| Rows DUPLICATED across the splits of one AVRO or ORC file (never an error) | **Check the FORMAT first.** The Avro and ORC readers materialize WHOLE files — they never read `task.start`/`task.length` — so any byte window handed to them re-emits the entire file and an N-way split returns N copies. `task.rs::reader_honors_byte_range` therefore makes `split` decline AVRO/ORC (they are splittable in the Java `FileFormat` table; `is_splittable` still ports that faithfully and is a SEPARATE predicate), and `../arrow/reader.rs::reject_ranged_whole_file_task` fails a ranged AVRO/ORC task closed with a typed `FeatureUnsupported` on the direct-reader / `PartitionWork` seams. Pins: `scan::task::tests::split_declines_formats_whose_reader_ignores_byte_ranges` + `arrow::reader::avro_scan_tests::avro_split_reads_every_row_exactly_once` / `avro_ranged_task_is_rejected_with_a_typed_error` / `orc_ranged_task_is_rejected_with_a_typed_error` (the ORC call site of the guard was unpinned until 2026-08-08 — deleting it left the whole suite green). If AVRO/ORC ever gain block/stripe-range reads, flip the predicate — do not flip `is_splittable` |
| Rows DUPLICATED across the splits of one PARQUET file (never an error) | Row-group selection for a ranged task must be MIDPOINT-in-`[start, end)` over REAL footer offsets (`../arrow/reader.rs::filter_row_groups_by_byte_range`, Java `ParquetMetadataConverter.filterFileMetaDataByMidpoint`). An *overlap* rule hands a straddling row group to both adjacent sub-tasks; a synthesized `4 + Σ compressed_size` offset model drifts on any file with padding/inline bloom filters (parquet-rs writes bloom filters `AfterRowGroup` by default) and duplicates even offsets-ALIGNED splits. Pins: `arrow::reader::tests::test_midpoint_selection_*`. NOTE: the `partition_work.rs` split-size-1024 "union ≡ `to_arrow`" pin is **not** coverage here — that fixture's single row group ends well inside the FIRST window (`[4, 467)` of a 3,003-byte file split at 1,024), so both rules select the same set (measured; annotated in-tree by `u3_annotation_planning_fixture_is_non_discriminating`, which asserts that no row group crosses a split boundary) |
| A file disappears from `plan_tasks` (ZERO rows) while `plan_files` still returns it | Check `task.length`. A whole-file task may carry the legacy sentinel `start == 0, length == 0` (the spelling every read path here accepts as whole-file: the Parquet byte-range gate, the `_pos` guard, `reject_ranged_whole_file_task`). `split` returns `[self]` for it; without that guard the fixed-size walk (`remaining = self.length`, `while remaining > 0`) emits ZERO sub-tasks and `mod.rs`'s `split_tasks.extend(task.split(split_size)?)` drops the file with no error. Java cannot reach this — `BaseFileScanTask.length()` is always the file size. Pins: `scan::task::tests::split_whole_file_length_sentinel_is_one_task_not_zero` + `arrow::reader::tests::test_whole_file_length_sentinel_survives_split_and_reads_every_row` |
| A split sub-task reads the WRONG BYTES of a file (rows from outside its window) | Check `task.start` AND `task.length` vs `file_size_in_bytes` on the PARENT that was split. `split`'s offsets-aware and fixed-size branches both treat the byte space as ABSOLUTE FROM ZERO and derive their extent from the FILE, so re-splitting an already-ranged task relocates its window to offset 0 (`start != 0`: re-reads the prefix it never owned, drops its tail) and re-splitting a PARTIAL parent (`start == 0`, `length < file_size_in_bytes`) runs the manifest-offset windows past the parent's end (offsets `[0,300,700]` on a parent owning `[0,500)` → `(0,300) (300,400) (700,0)`). `task.rs::split` branch (1a) therefore returns `[self]` for `start != 0 \|\| length != file_size_in_bytes`; Java forecloses both shapes structurally (its `SplitScanTask` is not `SplittableScanTask`, and `BaseFileScanTask.length()` is always the file size), this crate uses ONE public type for both. Pins: `scan::task::tests::split_of_an_already_ranged_task_is_a_passthrough_not_a_relocation` + `split_of_a_partial_parent_is_a_passthrough_not_an_over_read` + `arrow::reader::tests::test_split_of_a_ranged_task_reads_the_parents_rows_not_the_whole_file` |
| A `_pos`-projecting scan returns ZERO rows and a typed `FeatureUnsupported` per sub-task | The task was SPLIT. The `_pos` read path decodes the file in physical order with ordinals from zero, so `../arrow/reader.rs`'s `_pos` guard admits only `start == 0` with `length == 0 \|\| length == file_size_in_bytes` and fails every other window closed. Three sites carry the rule: `task.rs::split` branch (1c) (the PRIMITIVE — `split` is `pub` and reachable without either caller), `mod.rs::plan_tasks`'s `projects_pos`, and `mod.rs::expand_within_file_parallel_tasks`. The latter two are DEFENSIVE-but-redundant since U3 cycle 6; if rows vanish anyway, look for a fourth route that builds sub-tasks without calling `split`. Pins: `scan::task::tests::split_of_a_pos_projecting_task_is_a_passthrough` + `scan::tests::test_within_file_parallel_suppressed_when_pos_projected` |
| `to_arrow()` and `plan_tasks()` disagree on which rows a file yields | Compare the two offsets gates — they DELIBERATELY differ. `task.rs::split` accepts `!offsets.is_empty()` (Java parity: one offset ⇒ one window from that offset to EOF, so bytes before it are in no sub-task — Java loses the same rows), while `mod.rs::expand_within_file_parallel_tasks`'s `can_expand` requires `offsets.len() > 1` (a fork-local `to_arrow` optimisation must never disagree with a whole-file read, and one offset buys no parallelism). Honest manifests carry `offsets[0] == 4` and >1 entry, so neither answer is observable in practice — do NOT "fix" either site to match the other. Pins: `scan::task::tests::split_single_offset_takes_the_offsets_aware_branch` + `scan::tests::test_within_file_parallel_declines_a_single_split_offset` |
| A `_pos` scan fails with `FeatureUnsupported` on `plan_tasks` / `PartitionWork` while `to_arrow()` works | The `_pos` read path decodes whole files with ordinals from 0 and rejects every ranged task, so NEITHER split site may split under a `_pos` projection. `to_arrow`'s `expand_within_file_parallel_tasks` always suppressed itself; `mod.rs::plan_tasks` did not until 2026-08-08 and manufactured exactly the shape the reader refuses (measured: 0 rows, two typed errors). Pins: `scan::tests::test_plan_tasks_does_not_split_when_pos_is_projected` + `test_within_file_parallel_suppressed_when_pos_projected` |
| Deletes resurrect after partition-spec evolution | Partition maps must key by `(spec_id, partition)` (FK2.3), not `Struct` alone — same partition values under two specs must not cross-attach. Pins: `test_fk2_3_multi_spec_*` |
